## 一、系统概览

### 1.1 目标

构建一个多 Agent 协作系统，通过多轮对话挖掘用户模糊的自然语言需求，经过发散提问、归纳分析、拆解转化，最终输出可供 Coding Agent 直接开发的完整故事卡。

### 1.2 核心价值

| 问题 | 传统方式 | 本系统方案 |
|------|----------|------------|
| 需求模糊 | 反复沟通，耗时数天 | 结构化对话，1 小时内完成 |
| 需求遗漏 | 开发中途发现，返工 | 5W1H 框架系统性挖掘 |
| 理解偏差 | 开发做出来的不是想要的 | Gherkin 验收标准，无歧义 |
| 质量不稳定 | 依赖个人经验 | 4 Agent 协作 + 质量评估员把关 |

## 二、多 Agent 架构设计

### 2.1 Agent 角色总览

| Agent | 中文名 | 职责 | 触发条件 | 输出 | 自由度 |
|-------|--------|------|----------|------|--------|
| **Conversation Guide** | 对话引导者 | 与用户对话，挖掘需求 | 用户发起需求 | 对话记录 + 需求点列表 | 高 |
| **Requirement Analyst** | 需求分析师 | 结构化需求，优先级排序 | 对话完成 | 分类需求清单 | 中 |
| **Story Card Generator** | 故事卡生成器 | 拆解为开发故事卡 | 需求确认 | JSON 故事卡 | 低 |
| **Quality Evaluator** | 质量评估员 | 评估故事卡质量 | 生成完成 | 评估报告 + Pass/Fail | 中 |

### 2.2 设计原则

1. **职责分离**: 每个 Agent 专注一个环节，避免单 Agent 全流程导致的质量下降
2. **独立评估**: 评估员与生成器分离，避免"自产自销"的宽松评估
3. **上下文管理**: 长对话触发上下文重置，通过 Handoff 工件传递状态
4. **增量迭代**: 评估不通过 → 返工 → 再评估，直到质量达标

## 三、核心 Workflow

### 3.1 完整流程

```
┌──────────────────────────────────────────────────────────────────────┐
│                         需求挖掘完整流程                              │
└──────────────────────────────────────────────────────────────────────┘

  ┌─────────┐
  │  用户   │ 初始需求："我想做一个类似小红书的应用"
  └────┬────┘
       │
       ▼
  ┌─────────────────────────────────────────────────────────────────┐
  │  Phase 1: 需求挖掘 (多轮对话)                                    │
  │  Agent: 对话引导者                                               │
  │                                                                  │
  │  Turn 1: "能具体说说你想要哪些核心功能吗？"                       │
  │  Turn 2: "目标用户是谁？他们主要使用场景是什么？"                  │
  │  Turn 3: "内容类型主要是图文、视频还是混合？"                     │
  │  Turn 4: "需要社交功能吗？关注、点赞、评论？"                     │
  │  ...                                                             │
  │                                                                  │
  │  Output: 对话记录 + 需求点列表                                    │
  └─────────────────────────────────────────────────────────────────┘
       │
       ▼
  ┌─────────────────────────────────────────────────────────────────┐
  │  Phase 2: 需求分析 (结构化)                                      │
  │  Agent: 需求分析师                                               │
  │                                                                  │
  │  - 提取 23 个需求点                                                │
  │  - 分类：Must(8) / Should(10) / Could(5)                         │
  │  - 识别 3 个依赖关系                                              │
  │  - 标记 5 个待确认问题                                            │
  │                                                                  │
  │  Output: 结构化需求清单                                          │
  └─────────────────────────────────────────────────────────────────┘
       │
       ▼
  ┌─────────────────────────────────────────────────────────────────┐
  │  Phase 3: 故事卡生成 (拆解)                                      │
  │  Agent: 故事卡生成器                                             │
  │                                                                  │
  │  - 将每个需求点拆解为 1-3 个故事卡                                 │
  │  - 编写验收标准 (Gherkin 格式)                                    │
  │  - 估算复杂度                                                    │
  │  - 标记依赖关系                                                  │
  │                                                                  │
  │  Output: 故事卡列表 (JSON)                                       │
  └─────────────────────────────────────────────────────────────────┘
       │
       ▼
  ┌─────────────────────────────────────────────────────────────────┐
  │  Phase 4: 质量评估                                               │
  │  Agent: 质量评估员                                               │
  │                                                                  │
  │  - 评估每张故事卡                                                │
  │  - 平均分 4.2 → Pass                                             │
  │  - 2 张卡需要修改（验收标准不清晰）                                │
  │                                                                  │
  │  Output: 评估报告 + 最终故事卡清单                                │
  └─────────────────────────────────────────────────────────────────┘
       │
       ▼
  ┌─────────────────┐
  │  输出给 Coding   │ 可直接交给开发 Agent 的故事卡
  │  Agent 开发      │
  └─────────────────┘
```

### 3.2 状态流转

```
┌─────────────┐
│   Idle      │ 等待用户发起需求
└──────┬──────┘
       │ 用户发起
       ▼
┌─────────────┐
│  Digging    │ 对话引导者与用户多轮对话
└──────┬──────┘
       │ 对话完成 (≥5 轮，覆盖率>80%)
       ▼
┌─────────────┐
│  Analyzing  │ 需求分析师结构化需求
└──────┬──────┘
       │ 分析完成
       ▼
┌─────────────┐
│  Generating │ 故事卡生成器拆解故事卡
└──────┬──────┘
       │ 生成完成
       ▼
┌─────────────┐
│  Evaluating │ 质量评估员评估
└──────┬──────┘
       │
   ┌───┴───┐
   │       │
   ▼       ▼
┌─────┐ ┌──────┐
│ Pass│ │ Fail │
└──┬──┘ └──┬───┘
   │       │
   │       └──────→ 返回 Generating 修改
   │
   ▼
┌─────────────┐
│  Complete   │ 输出给 Coding Agent
└─────────────┘
```

## 四、上下文管理策略

### 4.1 为什么需要上下文重置

**问题**: 长对话导致 Agent"上下文焦虑"

- Token 使用接近上限时，Agent 开始匆忙收尾
- 对话超过 15 轮，Agent 迷失在细节中
- 话题切换后，旧上下文干扰新话题

**解决**: 上下文重置 + Handoff 工件

### 4.2 重置触发条件

| 条件 | 阈值 | 说明 |
|------|------|------|
| 对话轮数 | > 15 轮 | 防止用户疲劳和 Agent 迷失 |
| Token 使用 | > 80% | 预留安全余量 |
| 话题切换 | 检测到 | 用户明显开始新话题 |
| 会话超时 | > 30 分钟无活动 | 节省资源 |
| 用户请求 | 任意时刻 | 用户主动要求继续 |

### 4.3 Handoff 工件结构

```markdown
# 需求挖掘交接 - Session N → N+1

## 会话状态
- **阶段**: digging|analyzing|generating|evaluating
- **已完成轮数**: N
- **已提取需求**: N 个
- **已生成故事卡**: N 张

## 已确认需求
[List]

## 待确认问题
[List with IDs]

## 用户偏好
[平台、技术栈、约束等]

## 下一步计划
[下一个 Agent 应该做什么]

## 注意事项
[需要特别关注的点]
```

### 4.4 重置流程

```
1. 当前 Agent 完成当前阶段工作
2. 生成 Handoff 工件 (自动)
3. 更新需求状态文档
4. 清空当前会话上下文
5. 启动新 Agent，载入 Handoff 工件
6. 新 Agent 继续工作
```

## 六、与 Coding Agent 的交接

### 6.1 输入给 Coding Agent

| 内容 | 格式 | 用途 |
|------|------|------|
| 故事卡 JSON | feature-list.json | 开发任务清单 |
| 项目背景摘要 | Markdown (<500 字) | 理解业务上下文 |

```

         │

         │
```

## 七、关键设计决策

### 7.1 为什么需要 4 个 Agent？

| 方案 | 优点 | 缺点 | 选择 |
|------|------|------|------|
| 单 Agent 全流程 | 简单，上下文连续 | 容易迷失，质量不稳定 | ❌ |
| 2 Agent(对话 + 生成) | 平衡复杂度 | 缺少质量把关 | ❌ |
| 4 Agent 分离 | 职责清晰，质量可控 | 需要交接管理 | ✅ |

**决策理由**: 遵循 agent-harness 的"分离评估"原则，避免单 Agent 自产自销导致的质量下降。

### 7.2 对话轮次控制

- **最小轮次**: 5 轮（确保基本需求清晰）
- **最大轮次**: 20 轮（避免用户疲劳）
- **触发输出**: 用户主动说"够了"或需求覆盖率>80%

### 7.3 发散与归纳的平衡

```
对话引导者：发散思维
  - "还有吗？"
  - "如果是 XX 场景呢？"
  - "有没有考虑过 XX 功能？"

需求分析师：归纳思维
  - 合并重复需求
  - 识别核心 vs 边缘
  - 优先级排序

故事卡生成器：工程思维
  - 可开发性检查
  - 依赖关系梳理
  - 工作量估算

质量评估员：批判思维
  - 挑刺找问题
  - 确保无歧义
  - 把关质量
```

## 八、质量保障机制

### 8.1 评估标准

| 维度 | 权重 | 检查项 |
|------|------|--------|
| **完整性** | 3x | 角色/功能/价值三要素齐全 |
| **可测试性** | 2x | 验收标准可验证 |
| **原子性** | 1.5x | 单个故事卡可独立开发 |
| **清晰度** | 1.5x | 无歧义，开发可直接理解 |

### 8.2 评分计算

```
Final Score = (完整性×3 + 可测试性×2 + 原子性×1.5 + 清晰度×1.5) / 8
```

**通过阈值**: ≥ 4.0

### 8.3 评估结果处理

| 条件 | 处理 |
|------|------|
| 全部通过，均分≥4.5 | APPROVED - 直接输出 |
| 全部通过，均分≥4.0 | APPROVED_WITH_MINOR_FIXES - 小修后输出 |
| 1-3 张失败，均分≥3.5 | NEEDS_REVISION - 修改失败卡片 |
| >3 张失败或均分<3.5 | REJECT - 重大返工 |

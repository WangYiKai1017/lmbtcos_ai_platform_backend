**状态**: 设计稿

## 一、Agent 概述

### 1.1 角色定位

需求分析师是需求挖掘系统的**结构化引擎**，负责将对话引导者提取的原始需求点转化为结构化、优先级清晰、可追溯的需求规格说明。

**类比角色**:
- 📊 **数据分析师** - 从杂乱数据中提取洞察
- 🗂️ **图书管理员** - 分类整理信息
- ⚖️ **法官** - 权衡优先级
- 🔗 **架构师** - 识别依赖关系

### 1.2 核心职责

| 职责 | 说明 | 关键指标 |
|------|------|----------|
| 需求提取 | 从对话中识别所有需求点 | 提取率>95% |
| 去重合并 | 合并重复/相似需求 | 重复率<5% |
| 分类整理 | 功能/非功能分类 | 分类准确率>90% |
| 优先级排序 | MoSCoW 法则分类 | Must 占比 20-30% |
| 依赖识别 | 标记需求间依赖 | 依赖识别完整 |
| 风险标注 | 识别技术和业务风险 | 风险覆盖率>80% |

### 1.3 输入输出

```
输入:
├── 对话记录 (JSON transcript)
├── 提取的需求点列表 (带置信度)
├── 待确认问题列表
├── 用户偏好记录
└── 需求摘要

输出:
├── 功能需求列表 (分类 + 优先级)
├── 非功能需求列表 (带可测量指标)
├── 用户故事列表 (As a...I want...So that...)
├── 待确认问题 (带影响评估)
├── 风险列表 (概率×影响)
└── 需求依赖关系图
```

## 二、需求分析方法论

### 2.1 需求提取与巩固

#### 提取策略

从对话记录中提取需求，不仅依赖对话引导者的提取结果，还要：

1. **重新阅读完整对话** - 发现可能遗漏的隐含需求
2. **交叉验证** - 对比引导者提取的需求，补充遗漏
3. **上下文推断** - 从用户表述中推断未明说的需求

```
示例:

对话片段:
用户："用户应该能找回密码"
引导者提取："密码找回功能"

分析师补充提取:
- "密码找回功能"(func-003)
- "需要用户注册时绑定手机或邮箱"(func-004, 隐含前提)
- "找回密码需要身份验证"(func-005, 隐含流程)
```

#### 合并重复需求

**识别重复**:
- 语义相同但表述不同
- 同一功能在不同场景被提及
- 用户和 Agent 分别提到同一功能

**合并规则**:
```
原始需求:
- req-001: "用户可以登录"
- req-005: "登录功能要有"
- req-008: "用户需要能登录系统"

合并后:
func-001: "用户可以登录系统"
  - 来源：req-001, req-005, req-008
  - 讨论轮次：turn 3, turn 7, turn 11
  - 置信度：high (多次确认)
```

### 2.2 需求分类框架

#### 功能需求 (Functional Requirements)

定义：系统**做什么**，用户能执行的操作

**子分类**:

| 子分类 | 说明 | 示例 |
|--------|------|------|
| **用户操作** | 用户主动执行的动作 | 登录、注册、发布内容 |
| **系统行为** | 系统自动执行的动作 | 发送通知、数据同步 |
| **数据操作** | 数据的 CRUD | 存储用户信息、检索订单 |
| **集成接口** | 与外部系统交互 | 支付接口、短信 API |

**模板**:
```json
{
  "id": "func-001",
  "type": "functional",
  "subType": "userAction",
  "description": "用户可以使用手机号注册账号",
  "priority": "Must",
  "sourceTurns": [3, 5],
  "dependencies": [],
  "notes": ""
}
```

#### 非功能需求 (Non-Functional Requirements)

定义：系统**如何表现**，质量属性和约束

**子分类**:

| 子分类 | 说明 | 示例 |
|--------|------|------|
| **性能** | 响应时间、吞吐量 | "页面加载<2 秒" |
| **安全** | 认证、授权、加密 | "密码加密存储" |
| **可用性** | 易用性、可访问性 | "支持色盲用户" |
| **可靠性** | 容错、恢复能力 | "99.9% 可用性" |
| **可扩展性** | 支持用户/数据增长 | "支持 10 万并发" |
| **合规性** | 法律、法规要求 | "符合 GDPR" |

**模板** (必须包含可测量指标):
```json
{
  "id": "nfunc-001",
  "type": "nonFunctional",
  "subType": "performance",
  "description": "页面加载时间",
  "priority": "Must",
  "metric": "首屏加载时间 < 2 秒 (3G 网络)",
  "measurable": true,
  "validationMethod": "使用 Lighthouse 测量"
}
```

### 2.3 MoSCoW 优先级排序

#### 优先级定义

| 优先级 | 含义 | 占比建议 | 判断标准 |
|--------|------|----------|----------|
| **Must** | MVP 必需，无此不可用 | 20-30% | 系统无法运转 |
| **Should** | 重要，但可延后 | 40-50% | 显著影响体验 |
| **Could** | 锦上添花 | 20-30% | 有更好，无也行 |
| **Won't** | 明确排除 | - | 本次不做 |

#### 优先级判断流程

```
1. 问：没有这个功能，系统还能用吗？
   - 不能 → Must
   - 能 → 继续 2

2. 问：没有这个功能，用户体验会严重受损吗？
   - 会 → Should
   - 不会 → 继续 3

3. 问：这个功能能显著提升用户满意度吗？
   - 能 → Could
   - 不能 → Won't (或降级为 Could)
```

#### 优先级示例

```
Must (没有就无法使用):
- 用户可以注册/登录
- 核心业务流程 (如点餐的下单功能)
- 支付功能 (如果涉及交易)

Should (重要但可延后):
- 密码找回
- 订单历史查看
- 基础搜索功能

Could (锦上添花):
- 深色模式
- 分享功能
- 个性化主题

Won't (本次不做):
- 直播功能 (用户明确说暂时不需要)
- 电商功能 (规划中但不在本期)
```

### 2.4 依赖关系识别

#### 依赖类型

| 类型 | 说明 | 示例 |
|------|------|------|
| **前置依赖** | A 完成后才能做 B | 注册 → 登录 |
| **数据依赖** | B 需要 A 产生的数据 | 下单 → 订单详情 |
| **技术依赖** | B 依赖 A 的技术实现 | 前端 → 后端 API |
| **业务依赖** | 业务流程决定顺序 | 支付 → 发货 |

#### 依赖图示例

```
                    ┌─────────────┐
                    │ func-001    │
                    │ 用户注册     │
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │ func-002    │
                    │ 用户登录     │
                    └──────┬──────┘
                           │
          ┌────────────────┼────────────────┐
          │                │                │
   ┌──────▼──────┐ ┌──────▼──────┐ ┌──────▼──────┐
   │ func-003    │ │ func-004    │ │ func-005    │
   │ 浏览菜单     │ │ 下单        │ │ 个人中心     │
   └─────────────┘ └──────┬──────┘ └─────────────┘
                          │
                   ┌──────▼──────┐
                   │ func-006    │
                   │ 支付        │
                   └─────────────┘
```

#### 依赖标注格式

```json
{
  "id": "func-006",
  "description": "用户可以支付订单",
  "dependencies": [
    {
      "id": "func-004",
      "type": "data",
      "reason": "支付需要订单信息"
    },
    {
      "id": "func-002",
      "type": "business",
      "reason": "支付需要用户已登录"
    }
  ]
}
```

### 2.5 风险识别

#### 风险分类

| 类别 | 说明 | 示例 |
|------|------|------|
| **技术风险** | 技术实现难度 | "需要实时音视频，技术复杂" |
| **业务风险** | 业务模式不确定性 | "盈利模式不清晰" |
| **时间风险** | 工期紧张 | "2 个月上线，时间紧张" |
| **资源风险** | 人力/预算不足 | "预算有限，需控制成本" |
| **合规风险** | 法律法规风险 | "涉及用户数据，需合规" |

#### 风险评估矩阵

```
           影响 (Impact)
           低    中    高
        ┌─────┬─────┬─────┐
     高 │ 中  │ 高  │ 极高 │
  概    ├─────┼─────┼─────┤
  率  中 │ 低  │ 中  │ 高  │
 (P)    ├─────┼─────┼─────┤
     低 │ 极低 │ 低  │ 中  │
        └─────┴─────┴─────┘
```

#### 风险标注格式

```json
{
  "id": "risk-001",
  "category": "technical",
  "description": "需要集成短信服务商 API，可能遇到审核延迟",
  "probability": "medium",
  "impact": "high",
  "riskLevel": "high",
  "mitigation": "提前准备多个短信服务商，准备备用方案",
  "relatedRequirements": ["func-001"]
}
```

## 三、工作流程

### 3.1 分析流程

```
┌─────────────────┐
│ 1. 阅读输入材料  │ 对话记录 + 提取的需求
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 2. 提取与补充    │ 重新提取，补充遗漏
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 3. 去重合并      │ 合并重复需求
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 4. 分类          │ 功能 vs 非功能
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 5. 优先级排序    │ MoSCoW 分类
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 6. 识别依赖      │ 建立依赖关系
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 7. 识别风险      │ 标注风险点
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 8. 质量自检      │ 检查清单
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 9. 输出结果      │ 结构化需求文档
└─────────────────┘
```

### 3.2 质量自检清单

输出前，Agent 自我检查：

- [ ] 所有需求都有优先级标注
- [ ] Must 优先级占比在 20-30%
- [ ] 每个非功能需求有可测量指标
- [ ] 依赖关系已识别
- [ ] 风险已标注并给出缓解措施
- [ ] 无重复需求
- [ ] 所有需求可追溯至对话轮次
- [ ] 待确认问题已列出并标注影响

## 五、与其他 Agent 的交互

### 5.1 接收对话引导者的输入

**检查点**:
- [ ] 对话记录完整
- [ ] 需求点列表清晰
- [ ] 待确认问题已列出

**可能的问题处理**:
```
问题 1: 需求点过于简略
处理：重新阅读对话，补充细节，标注"推断"

问题 2: 存在矛盾表述
处理：标记为待确认问题，建议回访用户

问题 3: 明显遗漏 (如未问支付需求)
处理：标注"建议补充提问"，评估是否影响继续
```

### 5.2 交给故事卡生成器

**交接内容**:
- 结构化需求文档 (完整 JSON)
- 需求追溯矩阵
- 待确认问题列表
- 风险清单

**交接条件**:
- 需求分析完成并通过自检
- 用户确认需求 (如有确认环节)
- 关键待确认问题已解决或可延后

### 5.3 接收返工请求

**故事卡生成器可能要求**:
```
请求 1: "func-005 描述不够清晰，无法拆解"
处理：补充详细描述，或联系对话引导者澄清

请求 2: "func-008 和 func-012 有重叠，是否合并？"
处理：评估后决定合并或保持独立

请求 3: "缺少搜索功能的需求，是否遗漏？"
处理：检查对话记录，如确实遗漏则补充
```

## 八、实施注意事项

### 8.1 常见陷阱

| 陷阱 | 表现 | 避免方法 |
|------|------|----------|
| 过度推断 | 添加用户未提及的需求 | 标注"推断"，置信度降级 |
| 优先级通胀 | 太多 Must | 强制 20-30% 占比 |
| 模糊指标 | "快速响应" | 要求具体数字 |
| 依赖遗漏 | 未识别关键依赖 | 使用依赖检查清单 |

### 8.2 工具辅助

建议使用工具：
- 需求追溯矩阵生成器
- 依赖关系可视化工具
- 优先级分布检查器

### 8.3 性能优化

- 增量分析：边读对话边提取
- 缓存中间结果：避免重复处理
- 并行处理：分类和优先级可并行

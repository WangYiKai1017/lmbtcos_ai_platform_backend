# Agent 详细设计：故事卡生成器 (Story Card Generator)

**版本**: 1.0  
**创建时间**: 2026-04-01  
**状态**: 设计稿

---

## 一、Agent 概述

### 1.1 角色定位

故事卡生成器是需求挖掘系统的**工程转化引擎**，负责将结构化的需求规格说明转化为原子化、可测试、开发可直接执行的故事卡 (Story Cards)。

**类比角色**:
- 🏗️ **建筑设计师** - 将需求转化为施工图纸
- ✂️ **裁缝** - 将大布裁剪成合身的衣服
- 📋 **技术作家** - 编写清晰的技术文档
- 🎯 **项目经理** - 拆解任务并估算工时

### 1.2 核心职责

| 职责 | 说明 | 关键指标 |
|------|------|----------|
| 需求拆解 | 将需求拆分为原子故事卡 | 每需求 1-3 张卡 |
| 验收标准编写 | 编写 Gherkin 格式验收标准 | 每卡≥3 条 AC |
| 复杂度估算 | S/M/L/XL 工时评估 | 偏差<50% |
| 依赖标注 | 标记故事卡间依赖 | 依赖完整 |
| 技术注释 | 添加技术实现提示 | 关键卡有注释 |

### 1.3 输入输出

```
输入:
├── 功能需求列表 (已分类 + 优先级)
├── 非功能需求列表 (带指标)
├── 用户故事 (As a...格式)
├── 待确认问题
├── 风险清单
└── 需求依赖关系图

输出:
├── 故事卡列表 (JSON，完整格式)
├── Epic 分组
├── 依赖关系图 (故事卡级别)
├── 待确认问题 (关联到具体故事卡)
└── 实现建议 (技术栈、架构提示)
```

## 二、故事卡拆解方法论

### 2.1 原子化原则

**好的故事卡特征 **(INVEST 原则):

| 原则 | 含义 | 检查方法 |
|------|------|----------|
| **I**ndependent | 独立的 | 可单独开发测试 |
| **N**egotiable | 可协商的 | 实现方式可讨论 |
| **V**aluable | 有价值的 | 用户能感知价值 |
| **E**stimable | 可估算的 | 能评估工作量 |
| **S**mall | 小的 | 最好 S/M 规模 |
| **T**estable | 可测试的 | 有明确验收标准 |

### 2.2 拆解策略

#### 策略 1: 按工作流步骤拆解

```
原始需求："用户可以完成购物"

拆解为:
story-001: 用户可以浏览商品
story-002: 用户可以将商品加入购物车
story-003: 用户可以创建订单
story-004: 用户可以支付订单
story-005: 用户可以查看订单状态
```

#### 策略 2: 按用户角色拆解

```
原始需求："管理订单"

拆解为:
story-010 (顾客): 用户可以查看自己的订单
story-011 (商家): 商家可以查看店铺订单
story-012 (商家): 商家可以更新订单状态
story-013 (管理员): 管理员可以查看所有订单
```

#### 策略 3: 按 CRUD 操作拆解

```
原始需求："管理商品"

拆解为:
story-020: 商家可以创建商品
story-021: 商家可以查看商品列表
story-022: 商家可以编辑商品信息
story-023: 商家可以下架商品
story-024: 商家可以删除商品
```

#### 策略 4: 按数据类型拆解

```
原始需求："上传内容"

拆解为:
story-030: 用户可以上传图片
story-031: 用户可以上传视频
story-032: 用户可以上传文档
```

#### 策略 5: 按业务规则拆解

```
原始需求："订单折扣"

拆解为:
story-040: 订单满 100 元减 10 元
story-041: 会员享受 95 折
story-042: 使用优惠券享受优惠
story-043: 特价商品不参与其他优惠
```

### 2.3 拆解决策树

```
需求是否包含多个用户角色？
├─ 是 → 按角色拆解
└─ 否 → 继续

需求是否包含多个独立操作？
├─ 是 → 按操作拆解
└─ 否 → 继续

需求是否涉及多种数据类型？
├─ 是 → 按数据类型拆解
└─ 否 → 继续

需求是否有复杂的业务规则？
├─ 是 → 按规则拆解
└─ 否 → 可能不需要拆解，直接生成一张卡

拆解后的卡片是否仍然过大 (L/XL)?
├─ 是 → 继续按工作流步骤拆解
└─ 否 → 完成
```

## 三、验收标准编写

### 3.1 Gherkin 语法规范

**基本格式**:
```
Given [前置条件]
When [用户操作]
Then [预期结果]
And [额外结果]
```

### 3.2 验收标准质量要求

| 要求 | 说明 | 示例 |
|------|------|------|
| **具体** | 避免模糊词汇 | ✅ "显示红色错误提示"<br>❌ "显示错误" |
| **可测试** | 有明确 pass/fail | ✅ "加载时间<2 秒"<br>❌ "快速加载" |
| **完整** | 覆盖主流程 + 边缘 | ✅ 包含成功 + 失败场景<br>❌ 只有成功场景 |
| **独立** | 每条 AC 可独立验证 | ✅ 每条测试一个行为<br>❌ 多条混在一起 |

### 3.3 验收标准模板

#### 模板 1: 成功场景

```
AC-1:
Given 用户已打开登录页面
When 用户输入正确的手机号和密码
And 用户点击"登录"按钮
Then 用户成功登录
And 页面跳转到首页
And 顶部显示用户昵称
```

#### 模板 2: 失败场景

```
AC-2:
Given 用户在登录页面
When 用户输入错误的密码
And 用户点击"登录"按钮
Then 登录失败
And 显示错误提示"密码错误，请重试"
And 密码输入框被清空
And 用户可以重新输入
```

#### 模板 3: 边缘场景

```
AC-3:
Given 用户连续 5 次输入错误密码
When 用户第 6 次尝试登录
Then 账号被临时锁定
And 显示提示"账号已锁定，请 30 分钟后重试或重置密码"
And 锁定倒计时开始显示
```

#### 模板 4: 空状态

```
AC-4:
Given 用户是新用户，没有任何订单
When 用户打开订单列表页面
Then 显示空状态提示"暂无订单"
And 显示"去购物"按钮
And 不显示订单列表
```

### 3.4 每条故事卡的 AC 数量

| 故事卡规模 | AC 数量建议 | 说明 |
|------------|-------------|------|
| **S** | 2-3 条 | 简单功能 |
| **M** | 3-5 条 | 标准功能 |
| **L** | 5-7 条 | 复杂功能 |
| **XL** | 7+ 条 | 需要重新评估是否拆分 |

## 四、复杂度估算

### 4.1 估算标准

| 规模 | 工时 | 特征 | 示例 |
|------|------|------|------|
| **S** | < 4 小时 | 简单，无依赖，明确 | 静态页面、简单表单 |
| **M** | 4-16 小时 | 中等，1-2 个依赖 | 带 API 交互的功能 |
| **L** | 2-5 天 | 复杂，多依赖，有未知 | 涉及多模块协作 |
| **XL** | > 1 周 | 非常复杂，高不确定性 | 新技术、复杂算法 |

### 4.2 估算考虑因素

```
复杂度评分 = 基础分 + 调整分

基础分:
- S: 1 分
- M: 3 分
- L: 5 分
- XL: 8 分

调整分:
+1 分: 有外部 API 集成
+1 分: 涉及支付/安全
+1 分: 需要新 UI 组件
+1 分: 有性能要求
+1 分: 需要数据迁移
-1 分: 有现成模板/组件
-1 分: 团队熟悉该功能
```

### 4.3 估算示例

```
story-001: 手机号注册

基础评估: M (3 分) - 标准表单 + API 交互

调整因素:
+1: 需要集成短信 API
+1: 涉及用户安全
-1: 有现成表单组件

最终评分: 4 分 → M (4-16 小时)

备注: 短信 API 集成是主要不确定因素
```

## 五、技术注释编写

### 5.1 技术注释内容

| 类型 | 内容 | 示例 |
|------|------|------|
| **API 集成** | 需要调用的外部 API | "需要集成阿里云短信 API" |
| **数据库** | 数据表设计提示 | "需要 users 表，字段：phone, password_hash" |
| **安全** | 安全相关注意事项 | "密码使用 bcrypt 加密，cost=12" |
| **性能** | 性能优化提示 | "列表需要分页，每页 20 条" |
| **依赖** | 技术依赖说明 | "依赖 story-002 的登录功能" |

### 5.2 技术注释示例

```json
{
  "id": "story-001",
  "title": "用户可以使用手机号注册",
  "technicalNotes": "1. 使用阿里云短信服务发送验证码\n2. 验证码存储到 Redis，TTL=5 分钟\n3. 密码使用 bcrypt 加密 (cost=12)\n4. 需要防刷机制：同一手机号每天最多 10 次\n5. 数据库表：users(id, phone, password_hash, created_at)"
}
```

## 七、工作流程

### 7.1 生成流程

```
┌─────────────────┐
│ 1. 阅读需求文档  │ 功能需求 + 非功能需求
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 2. 识别 Epic     │ 按业务领域分组
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 3. 逐需求拆解    │ 应用拆解策略
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 4. 编写验收标准  │ Gherkin 格式
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 5. 估算复杂度    │ S/M/L/XL
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 6. 标注依赖      │ 故事卡级别依赖
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 7. 添加技术注释  │ 实现提示
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 8. 质量自检      │ 检查清单
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 9. 输出故事卡    │ 完整 JSON
└─────────────────┘
```

### 7.2 质量自检清单

输出前，Agent 自我检查：

- [ ] 每张卡有完整 7 要素 (ID/标题/描述/AC/优先级/复杂度/依赖)
- [ ] 标题使用"User can..."格式
- [ ] 描述使用"As a...I want...So that..."格式
- [ ] 每张卡至少 3 条验收标准
- [ ] 验收标准使用 Gherkin 格式
- [ ] 验收标准可测试 (pass/fail 明确)
- [ ] 复杂度估算合理
- [ ] 依赖关系正确
- [ ] 无模糊词汇 ("快速"、"友好"等)
- [ ] 技术注释包含关键实现点

## 八、与其他 Agent 的交互

### 8.1 接收需求分析师的输入

**检查点**:
- [ ] 需求文档完整
- [ ] 优先级清晰
- [ ] 依赖关系明确

**可能的问题处理**:
```
问题 1: 需求描述模糊
处理：基于上下文推断，标注"推断"，置信度降级

问题 2: 需求之间有冲突
处理：标注冲突，建议需求分析师澄清

问题 3: 缺少非功能需求
处理：基于行业标准补充默认值，标注"补充"
```

### 8.2 交给质量评估员

**交接内容**:
- 完整故事卡 JSON
- Epic 分组
- 依赖关系图
- 待确认问题

**交接条件**:
- 故事卡生成完成并通过自检
- 所有需求已拆解
- 无明显的模糊或遗漏

### 8.3 接收返工请求

**质量评估员可能要求**:
```
请求 1: "story-005 的 AC-2 不可测试"
处理：重写 AC-2，使其具体可测量

请求 2: "story-008 太大，建议拆分"
处理：按工作流步骤拆分为 story-008a, story-008b

请求 3: "缺少错误场景的 AC"
处理：补充失败场景的验收标准
```

## 九、质量标准

### 9.1 故事卡质量指标

| 指标 | 目标值 | 测量方式 |
|------|--------|----------|
| 完整性 | 100% | 7 要素检查 |
| 可测试性 | >95% | AC 可 pass/fail |
| 原子性 | >90% | 可独立开发 |
| 清晰度 | >90% | 开发无疑问 |
| 估算准确率 | >70% | 与实际对比 |

### 9.2 常见问题与修复

| 问题 | 表现 | 修复方法 |
|------|------|----------|
| AC 模糊 | "应该正常工作" | 改为具体行为描述 |
| 卡片过大 | XL 占比>10% | 继续拆分 |
| 依赖遗漏 | 开发时发现依赖 | 补充依赖关系 |
| 技术注释缺失 | 开发有疑问 | 补充关键实现点 |

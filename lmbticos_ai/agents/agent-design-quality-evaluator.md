# Agent 详细设计：质量评估员 (Quality Evaluator)

**版本**: 1.0  
**创建时间**: 2026-04-01  
**状态**: 设计稿

---

## 一、Agent 概述

### 1.1 角色定位

质量评估员是需求挖掘系统的**质量守门员**，负责以批判性、独立的视角评估故事卡质量，确保输出给 Coding Agent 的故事卡达到开发就绪标准。

**类比角色**:
- 👁️ **质检员** - 产品出厂前的最后检查
- ⚖️ **审计师** - 独立、客观、批判性
- 🎯 **教练** - 指出问题并给出改进建议
- 🛡️ **守门员** - 阻止低质量卡片流向开发

### 1.2 核心职责

| 职责 | 说明 | 关键指标 |
|------|------|----------|
| 故事卡评估 | 逐卡评估质量 | 评估覆盖率 100% |
| 评分计算 | 4 维度加权评分 | 评分一致性>85% |
| 缺陷识别 | 找出问题和不足 | 缺陷检出率>90% |
| 反馈生成 | 提供具体改进建议 | 建议可执行率>95% |
| 通过决策 | Pass/Fail 决定 | 决策合理性>90% |
| 质量报告 | 生成整体质量报告 | 报告完整清晰 |

### 1.3 输入输出

```
输入:
├── 故事卡列表 (完整 JSON)
├── Epic 分组
├── 依赖关系图
├── 原始需求文档 (追溯用)
└── 用户偏好记录

输出:
├── 逐卡评估报告 (带评分)
├── 整体质量报告
├── 必修复问题清单
├── 建议修复问题清单
├── Pass/Fail 决定
└── 质量改进建议
```

### 1.4 核心设计原则

| 原则 | 说明 | 实施要点 |
|------|------|----------|
| **独立性** | 与生成器分离 | 不评估自己的工作 |
| **批判性** | 默认怀疑态度 | 证明质量好，而非证明质量差 |
| **具体性** | 反馈具体可执行 | 指出具体问题 + 修改建议 |
| **一致性** | 评分标准统一 | 使用评分量表和示例 |
| **建设性** | 帮助改进 | 不仅挑错，也给出方向 |

## 二、评估框架

### 2.1 四维度评估模型

```
                    故事卡质量
                        │
        ┌───────────────┼───────────────┐
        │               │               │
   ┌────▼────┐    ┌────▼────┐    ┌────▼────┐
   │ 完整性   │    │ 可测试性 │    │ 原子性   │
   │ (3x)    │    │ (2x)    │    │ (1.5x)  │
   └─────────┘    └─────────┘    └─────────┘
                        │
                   ┌────▼────┐
                   │ 清晰度   │
                   │ (1.5x)  │
                   └─────────┘

最终得分 = (完整性×3 + 可测试性×2 + 原子性×1.5 + 清晰度×1.5) / 8
```

### 2.2 完整性评估 (Completeness)

**权重**: 3x (最高)

**检查项**:

| 检查项 | 要求 | 分值 |
|--------|------|------|
| 标题格式 | "User can..." | 1 分 |
| 描述格式 | "As a...I want...So that..." | 2 分 |
| AC 数量 | ≥3 条 | 2 分 |
| AC 格式 | Given/When/Then | 2 分 |
| 优先级 | Must/Should/Could | 1 分 |
| 复杂度 | S/M/L/XL | 1 分 |
| 依赖 | 已标注或明确无 | 1 分 |

**评分标准**:

| 分数 | 标准 |
|------|------|
| **5 分** | 所有字段完整且高质量，无缺失 |
| **4 分** | 所有字段存在，1-2 处小瑕疵 |
| **3 分** | 大部分字段存在，3-4 处问题 |
| **2 分** | 缺失关键字段 (如 AC<2 条) |
| **1 分** | 严重不完整，无法使用 |

**示例评估**:

```
story-001 评估:
✅ 标题："用户可以使用手机号注册" - 符合"User can"格式
✅ 描述："作为新用户，我想要...以便..." - 完整三段式
✅ AC 数量：5 条 - 充足
✅ AC 格式：全部使用 Given/When/Then
✅ 优先级：Must - 已标注
✅ 复杂度：M - 已标注
✅ 依赖：[] - 明确无依赖

得分：5/5
评语：完整性优秀，所有必需字段完整且格式正确
```

### 2.3 可测试性评估 (Testability)

**权重**: 2x

**检查项**:

| 检查项 | 要求 | 示例 |
|--------|------|------|
| AC 可验证 | Pass/Fail 明确 | ✅ "显示红色错误"<br>❌ "显示错误" |
| 无模糊词 | 避免"快速"、"友好" | ✅ "<2 秒"<br>❌ "快速" |
| 场景覆盖 | 成功 + 失败 + 边缘 | ✅ 覆盖 3 类场景<br>❌ 只有成功场景 |
| 前置条件 | Given 清晰 | ✅ "用户已登录"<br>❌ "用户..." |
| 操作具体 | When 描述具体动作 | ✅ "点击登录按钮"<br>❌ "进行操作" |
| 结果可测 | Then 可验证 | ✅ "跳转到首页"<br>❌ "体验良好" |

**评分标准**:

| 分数 | 标准 |
|------|------|
| **5 分** | 所有 AC 立即可测试，无歧义 |
| **4 分** | 大部分 AC 可测试，1-2 处需澄清 |
| **3 分** | 部分 AC 模糊，但可修复 |
| **2 分** | 多数 AC 不可测试 |
| **1 分** | AC 无法验证 |

**示例评估**:

```
story-002 评估:

AC-1: "Given 用户在登录页面，When 输入正确密码，Then 登录成功"
  → ❌ "登录成功"不具体，应说明跳转到哪里、显示什么
  → 建议修改："Then 登录成功，页面跳转到首页，顶部显示用户昵称"

AC-2: "Given 用户输入错误密码，When 点击登录，Then 显示错误"
  → ❌ "显示错误"不具体，应说明显示在哪里、什么内容
  → 建议修改："Then 显示红色错误提示'密码错误，请重试'在输入框下方"

AC-3: "Given 用户连续 5 次失败，When 第 6 次尝试，Then 账号锁定"
  → ✅ 具体可测

得分：3/5
评语：AC-1 和 AC-2 需要补充具体结果描述
```

### 2.4 原子性评估 (Atomicity)

**权重**: 1.5x

**检查项**:

| 检查项 | 要求 | 示例 |
|--------|------|------|
| 单一目标 | 一张卡一个用户目标 | ✅ "用户可以登录"<br>❌ "用户可以登录和注册" |
| 独立开发 | 可独立于其他卡开发 | ✅ 依赖明确<br>❌ 隐含依赖 |
| 规模适当 | 最好 S/M，避免 L/XL | ✅ M 规模<br>❌ XL 未拆分 |
| 无混合关注 | 不混入不相关功能 | ✅ 专注单一功能<br>❌ 混杂多个功能 |

**评分标准**:

| 分数 | 标准 |
|------|------|
| **5 分** | 完美原子化，专注单一目标 |
| **4 分** | 基本原子化，可考虑微调 |
| **3 分** | 可拆分为 2 张卡 |
| **2 分** | 明显包含 2-3 个功能 |
| **1 分** | 史诗级，需要重大拆分 |

**示例评估**:

```
story-005 评估:

标题："用户可以管理个人资料（查看、编辑、上传头像、修改密码）"
  → ❌ 包含 4 个独立功能
  → 建议拆分为:
     - story-005a: 用户可以查看个人资料
     - story-005b: 用户可以编辑个人资料
     - story-005c: 用户可以上传头像
     - story-005d: 用户可以修改密码

得分：2/5
评语：包含过多功能，建议拆分为 4 张独立故事卡
```

### 2.5 清晰度评估 (Clarity)

**权重**: 1.5x

**检查项**:

| 检查项 | 要求 | 示例 |
|--------|------|------|
| 无歧义 | 只有一种理解 | ✅ "红色按钮"<br>❌ "醒目的按钮" |
| 术语一致 | 全文术语统一 | ✅ 统一用"登录"<br>❌ 混用"登录/登陆" |
| 技术注释 | 关键实现点清晰 | ✅ 包含 API、数据表 |
| UX 注释 | 交互细节清晰 | ✅ 包含动画、提示 |
| 开发者友好 | 开发可直接理解 | ✅ 无疑问<br>❌ 需要多次询问 |

**评分标准**:

| 分数 | 标准 |
|------|------|
| **5 分** | 极其清晰，开发无需询问 |
| **4 分** | 清晰，1-2 处小疑问 |
| **3 分** | 基本清晰，部分需要澄清 |
| **2 分** | 多处歧义，影响开发 |
| **1 分** | 难以理解 |

**示例评估**:

```
story-008 评估:

问题 1: "用户友好"出现 3 次
  → ❌ 主观词汇，不同人理解不同
  → 建议改为具体行为描述

问题 2: "快速响应"
  → ❌ 不具体
  → 建议改为"响应时间<500ms"

问题 3: 技术注释缺失
  → ❌ 未说明使用哪个 API
  → 建议补充"调用/user/profile API"

得分：3/5
评语：存在多处模糊表述，需要具体化
```

## 三、评分计算与决策

### 3.1 评分计算公式

```
故事卡得分 = (完整性×3 + 可测试性×2 + 原子性×1.5 + 清晰度×1.5) / 8

项目总分 = 所有故事卡得分的平均值
```

### 3.2 通过决策矩阵

| 条件 | 决定 | 说明 |
|------|------|------|
| 所有卡≥4.0，均分≥4.5 | **APPROVED** | 高质量，直接通过 |
| 所有卡≥4.0，均分≥4.0 | **APPROVED_WITH_FIXES** | 通过，需小修 |
| 1-3 张卡<4.0，均分≥3.5 | **NEEDS_REVISION** | 修改失败卡片 |
| >3 张卡<4.0 或 均分<3.5 | **REJECT** | 重大返工 |

### 3.3 决策示例

```
项目 A:
- 总卡片：24 张
- 通过卡片：24 张 (全部≥4.0)
- 平均分：4.6
- 最低分：4.2
- 最高分：5.0

决定：APPROVED
评语：优秀，可直接交给开发团队

---

项目 B:
- 总卡片：20 张
- 通过卡片：18 张
- 失败卡片：2 张 (3.5 和 3.8)
- 平均分：4.1
- 最低分：3.5
- 最高分：4.9

决定：NEEDS_REVISION
评语：修改 2 张失败卡片后重新评估

---

项目 C:
- 总卡片：30 张
- 通过卡片：15 张
- 失败卡片：15 张
- 平均分：3.2
- 最低分：1.5
- 最高分：4.5

决定：REJECT
评语：质量问题较多，建议重大返工后重新生成
```

## 四、反馈生成

### 4.1 反馈质量要求

| 要求 | 说明 | 示例 |
|------|------|------|
| **具体** | 指出具体问题位置 | ✅ "AC-2 的 Then 部分"<br>❌ "有些地方" |
| **可执行** | 给出修改方向 | ✅ "补充错误消息内容"<br>❌ "改进一下" |
| **优先级** | 区分必改和选改 | ✅ "必改：... 选改：..."<br>❌ 全部混在一起 |
| **友善** | 建设性语气 | ✅ "建议补充..."<br>❌ "这写得太差了" |

### 4.2 反馈模板

```markdown
## story-XXX 评估反馈

### 整体评分：X.X/5.0 [Pass/Fail]

### 维度得分
- 完整性：X/5
- 可测试性：X/5
- 原子性：X/5
- 清晰度：X/5

### 必修复问题 (Blocking)

1. **问题**: [具体描述]
   - **位置**: AC-2 的 Then 部分
   - **影响**: 开发无法确定具体实现
   - **建议**: 修改为"[具体修改建议]"

2. **问题**: [具体描述]
   - **位置**: 技术注释
   - **影响**: 缺少关键 API 信息
   - **建议**: 补充"调用 XXX API"

### 建议修复问题 (Recommended)

1. **问题**: [具体描述]
   - **建议**: [改进建议]

### 优点

- [做得好的地方 1]
- [做得好的地方 2]

### 修改后示例

```json
[展示修改后的完整故事卡]
```
```

### 4.3 反馈示例

```markdown
## story-005 评估反馈

### 整体评分：3.5/5.0 ❌ Fail

### 维度得分
- 完整性：4/5 ✅
- 可测试性：3/5 ⚠️
- 原子性：2/5 ❌
- 清晰度：4/5 ✅

### 必修复问题 (Blocking)

1. **问题**: 故事卡包含过多功能
   - **位置**: 标题和描述
   - **影响**: 无法估算工时，开发难以聚焦
   - **建议**: 拆分为 4 张独立卡片:
     - story-005a: 查看个人资料
     - story-005b: 编辑个人资料
     - story-005c: 上传头像
     - story-005d: 修改密码

2. **问题**: AC-2 结果不具体
   - **位置**: AC-2 的 Then 部分
   - **影响**: 开发不知道显示什么错误
   - **建议**: 修改为"Then 显示红色错误提示'邮箱格式不正确'在输入框下方"

### 建议修复问题 (Recommended)

1. **问题**: 缺少技术注释
   - **建议**: 补充"调用 GET /user/profile 和 PUT /user/profile API"

2. **问题**: 缺少 UX 注释
   - **建议**: 补充"头像上传支持拖拽，显示进度条"

### 优点

- AC 覆盖了成功和失败场景 ✅
- 描述使用了标准格式 ✅

## 五、工作流程

### 5.1 评估流程

```
┌─────────────────┐
│ 1. 接收故事卡    │ 从故事卡生成器
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 2. 逐卡评估      │ 四维度评分
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 3. 计算得分      │ 加权平均
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 4. 生成反馈      │ 具体改进建议
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 5. 做出决定      │ Pass/Fail
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 6. 生成报告      │ 整体质量报告
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 7. 输出结果      │ 评估报告 + 决定
└─────────────────┘
```

### 5.2 质量自检

输出前，评估员自我检查：

- [ ] 所有故事卡已评估
- [ ] 评分一致，无双重标准
- [ ] 反馈具体可执行
- [ ] 必改问题已标注
- [ ] 决策符合决策矩阵
- [ ] 语气建设性，非攻击性

## 六、与其他 Agent 的交互

### 6.1 接收故事卡生成器的输入

**检查点**:
- [ ] 故事卡格式完整
- [ ] 数量与需求匹配
- [ ] 无明显遗漏

**可能的问题处理**:
```
问题 1: 故事卡数量远少于需求
处理：询问是否遗漏，或标注"覆盖不全"

问题 2: 格式严重不规范
处理：降低清晰度评分，建议重新生成
```

### 6.2 输出给故事卡生成器 (返工)

**返工要求**:
```
包含:
- 失败卡片列表
- 每张卡的具体问题
- 修改建议
- 修改后示例

不包含:
- 人身攻击语气
- 模糊的批评
- 无法执行的建议
```

### 6.3 输出给 Coding Agent (通过)

**交接内容**:
```
- 完整故事卡 JSON (已修复)
- 评估报告摘要
- 已知问题列表 (如有)
- 质量评分
```

## 七、质量标准

### 7.1 评估质量指标

| 指标 | 目标值 | 测量方式 |
|------|--------|----------|
| 评估一致性 | >85% | 同卡多次评估对比 |
| 缺陷检出率 | >90% | 与人工评审对比 |
| 反馈可执行率 | >95% | 生成器能否按反馈修改 |
| 决策合理性 | >90% | 与人工决策对比 |

### 7.2 评估员偏差控制

| 偏差类型 | 表现 | 控制方法 |
|----------|------|----------|
| 宽容偏差 | 评分普遍偏高 | 使用严格量表 |
| 严格偏差 | 评分普遍偏低 | 定期校准 |
| 近因效应 | 后期评分偏离 | 随机顺序评估 |
| 光环效应 | 一好全好 | 分维度独立评分 |

## 九、实施注意事项

### 9.1 评估员人设

**推荐人设**: 严格但友善的资深技术主管

**语气示例**:
- ✅ "这个 AC 需要更具体，建议补充..."
- ✅ "这里有个问题：... 建议修改为..."
- ✅ "做得好的地方：... 需要改进的：..."
- ❌ "这写得太差了"
- ❌ "完全不可用"
- ❌ "重写"

### 9.2 评分校准

定期校准评分标准:
- 每周 review 评估样本
- 对比人工评审结果
- 调整评分量表

### 9.3 持续学习

- 收集开发反馈：哪些故事卡实际开发顺利
- 对比评估分与实际质量
- 调整评估维度和权重

## 十、常见评估场景处理

### 场景 1: 边界情况 (3.9 分 vs 4.0 分)

```
原则: 就低不就高

处理:
- 3.9 分 → Fail，需要修改
- 给出具体修改建议
- 修改后重新评估

理由: 4.0 是质量标准，不应妥协
```

### 场景 2: 大部分优秀，少数失败

```
原则: 木桶效应

处理:
- 不因大部分优秀而放宽失败卡片
- 每张卡独立评估
- 失败卡片必须修改

理由: 开发遇到困难卡片会阻塞进度
```

### 场景 3: 整体质量差

```
原则: 早期止损

处理:
- 直接 REJECT
- 给出整体改进建议
- 建议重新生成

理由: 小修小补无法解决系统性问题
```
